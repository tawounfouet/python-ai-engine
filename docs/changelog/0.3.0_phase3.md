# Changelog - Version 0.3.0 (Phase 3 : Services Layer)

**Date** : Mars 2026

## Vue d'ensemble

Phase 3 introduit la couche services : l'orchestration complète des agents LLM, l'abstraction universelle des providers, et la boucle de chat avec gestion automatique du contexte. C'est la première phase où le moteur est fonctionnellement utilisable de bout en bout — d'un provider configuré jusqu'à une réponse LLM persistée.

---

## Ajouts ✨

### 🧠 Interface abstraite LLM (`src/ai_engine/services/llm/base.py`)

- **`LLMClient` ABC** — Interface commune à tous les clients LLM :
  - `complete(request: LLMRequest) → LLMResponse` : complétion **synchrone** (obligatoire)
  - `acomplete(request: LLMRequest) → LLMResponse` : complétion **asynchrone** (obligatoire)
  - `stream(request: LLMRequest) → Iterator[StreamChunk]` : streaming **synchrone** (obligatoire)
  - `astream(request: LLMRequest) → AsyncIterator[StreamChunk]` : streaming **asynchrone** (obligatoire)
  - `chat(messages, model, temperature, **kwargs)` : interface simplifiée sync (accepte `str` ou `list[Message]`)
  - `achat(...)` : version async de `chat()`
  - `get_model()` : retourne le modèle par défaut du provider
  - `get_base_config()` : dict de configuration (model, temperature, max_tokens, top_p, penalties)
  - `validate_capabilities(request)` : vérifie streaming, function_calling, vision contre les `ProviderCapabilities`
  - Support du context manager (`__enter__` / `__exit__`) pour un usage avec `with`

- **`LLMRequest`** (Pydantic) — Requête LLM unifiée :
  - `messages: list[Message]`, `model`, `temperature`, `max_tokens`, `stream`
  - `tools: list[dict]`, `tool_choice` (function calling)
  - `top_p`, `frequency_penalty`, `presence_penalty`, `stop`

- **`LLMResponse`** (Pydantic) — Réponse LLM unifiée :
  - `id`, `content`, `role`, `model`, `finish_reason`
  - `tool_calls: list[ToolCall]`
  - `usage: TokenUsage | None` (prompt/completion/total tokens)
  - `response_time_ms: float | None`
  - `to_message()` : conversion directe en `Message` Pydantic pour persistance

- **`StreamChunk`** (Pydantic) — Fragment de réponse streamée : `delta`, `finish_reason`, `tool_calls`

### 🔌 Cinq clients LLM concrets (`src/ai_engine/services/llm/`)

Chaque client : dépendance **optionnelle** (ImportError clair au lieu de crash silencieux), support sync/async/stream/astream, mesure de `response_time_ms`, conversion automatique des formats de messages vers le format natif du provider.

| Client | Fichier | Package requis | Notes |
|--------|---------|----------------|-------|
| `OpenAIClient` | `openai.py` | `openai` | Support `api_base_url` (Azure OpenAI, proxies), tool_calls |
| `AnthropicClient` | `anthropic.py` | `anthropic` | Conversion system prompt (séparé dans l'API Anthropic) |
| `OllamaClient` | `ollama.py` | `ollama` | `api_base_url` défaut `http://localhost:11434`, modèles locaux |
| `GroqClient` | `groq.py` | `groq` | Interface compatible OpenAI, vitesse d'inférence élevée |
| `GeminiClient` | `gemini.py` | `google-generativeai` | Conversion format messages Google |

### 🏭 LLM Factory (`src/ai_engine/services/llm/factory.py`)

- **`get_llm_client(provider_config: LLMProviderConfig) → LLMClient`** — Factory centrale :
  - Dispatch par `provider_config.provider_type` (`ProviderType` enum)
  - Providers supportés : `OPENAI`, `ANTHROPIC`, `OLLAMA`, `GROQ`, `GEMINI`
  - `ImportError` reformaté : message explicite avec la commande d'installation (`pip install ai-engine[<provider>]`)
  - `UnsupportedProviderError` : liste les types supportés dans le message

- **`list_available_providers() → list[ProviderType]`** — Introspection des dépendances installées :
  - Tente d'instancier chaque client ; retourne uniquement les providers utilisables dans l'environnement courant

### 🤖 `AgentService` (`src/ai_engine/services/agent.py`)

Service principal d'orchestration — dépend uniquement de `StorageBackend` (injecté) et de la LLM Factory :

- **`__init__(storage, tool_registry=None)`** : instancie automatiquement `ToolRegistry` + `ToolExecutor` si non fournis

- **Gestion des agents** :
  - `create_agent(name, provider_id, system_prompt, role, config, **kwargs) → Agent` : vérifie l'existence du provider, génère le slug auto, sauvegarde
  - `get_agent(agent_id) → Agent` : lève `AgentNotFoundError` si absent
  - `update_agent(agent_id, **updates) → Agent` : met à jour dynamiquement les champs + `updated_at`
  - `delete_agent(agent_id) → bool`
  - `list_agents(owner_id, role, is_active) → list[Agent]`
  - `get_agent_stats(agent_id) → dict` : compteurs de conversations et messages

- **Gestion des conversations** :
  - `create_conversation(agent_id, title, metadata) → Conversation` : titre auto `"Conversation with {agent.name}"`

- **Boucle de chat** — `chat(agent_id, message, conversation_id, **llm_options) → tuple[Message, Conversation]` :
  1. Récupère l'agent + son provider (lève `ProviderNotFoundError` si absent)
  2. Crée ou récupère la `Conversation` existante
  3. Sauvegarde le message utilisateur via `storage.save_message()`
  4. Compile le contexte via `_build_conversation_context()` : system prompt + historique récent (max 50 messages)
  5. Instancie le `LLMClient` via la factory
  6. **Branche outil** : si `agent.config.enable_tools` et outils enregistrés → `ToolExecutor.run_tool_loop()` (boucle tool-calling multi-tours)
  7. **Branche simple** : sinon → `llm_client.complete(LLMRequest(...))`
  8. Sauvegarde la réponse assistant + met à jour `conversation.updated_at`
  9. Retourne `(assistant_message, conversation)`

- **`_build_conversation_context(agent, conversation_id, max_messages=50)`** :
  - Préfixe le system prompt de l'agent comme `MessageRole.SYSTEM`
  - Concatène l'historique récent récupéré depuis le storage

- **`get_conversation_history(conversation_id, limit, offset) → list[Message]`** : pagination de l'historique
